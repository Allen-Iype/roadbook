# Phase 9 design brief — UI refinement

Status: DRAFT, awaiting Gate 1 review. One scope input is deliberately
missing (§2) and one is pending at the review itself (the maintainer's own
item list). No code before this brief is agreed.

Phase 6 built the design system and the two core surfaces; phases 7–8 put
real users in front of them. This phase refines the UI now that every
surface carries real data and real visitors: it closes the known gaps from
the phase 6 log, absorbs the UI backlog, and takes on the one structural
addition the maintainer has asked for — adventures as a browsable grid of
plate covers. `docs/phase-6/DESIGN.md` remains binding throughout: this
phase works *within* the Atlas plate system. Changing the direction itself
would require the phase 6 Stage B treatment (mockups reviewed at a STOP)
and is not proposed here.

## 1. Concepts this phase introduces

**The refinement/new-IA fork.** Not every UI change is the same kind of
work. This phase sorts every item into one of three buckets, and the bucket
determines the process:

- *Refinement in system* — the surface and its place in the app already
  exist; the work applies the binding design system better (a missing
  element, a legibility fix, a screen size never exercised). Brief-then-
  build, no mockups.
- *Mockup-gated new IA* — a new navigational element or surface. These get
  a miniature Stage B: static mockups reviewed at a STOP before any code,
  because an IA mistake is expensive to walk back once pages link to it.
- *Charter-level, excluded* — work that would change what the product *is*
  (authentication is the live example). Named here so its absence is a
  decision, not an oversight.

**Playwright as a layout harness — built first.** Phase 7 proved
small-screen claims with a throwaway puppeteer walk (~30 assertions,
regenerated by hand each time). This phase promotes that pattern to a
committed suite, and builds it as the *first* checkpoint so the
refinement sweep is assertion-driven rather than eyeball-driven: extend
the suite to a surface, watch the known gaps fail, fix to green. Every
later checkpoint then lands with the guard already in place and only adds
specs. Playwright rather than more puppeteer: it ships a test runner,
viewport fixtures, and auto-waiting assertions, so the suite is
declarative where the walk script was imperative. Scope is *layout truths
only* — no horizontal scroll, ≥44 px tap targets, tables fold at phone
width, dialog focus behaviour — at 390/768/1280 px against the compose
demo stack. Explicitly out: map-pixel visual regression (WebGL canvases
without `preserveDrawingBuffer` capture blank, rAF suspends in occluded
windows, tiles come from a third party — all three documented traps). The
map gets smoke checks only. `docs/screens/capture.js` (puppeteer) remains
the separate screenshot-record tool; two tools, two jobs, stated here so
the duplication is deliberate and does not drift into a merge.

**Route thumbnails as static SVG.** The grid (§4, CP4) and the life-map
hover card both want a small picture of a journey's shape. The obvious
tool — a MapLibre instance per tile — is the wrong one: WebGL contexts are
capped per page (~8–16), and a grid of tens of tiles would exhaust them.
The right tool already exists in this repo: the `/welcome` plate renders
journey geometry as plain SVG paths. A thumbnail is the same idea
generalised — project the leg polylines into a small viewBox, style by the
same four-way kind encoding, no basemap, no tiles, no runtime cost beyond
the geometry already fetched. Rejected alternative: pre-rendered raster
thumbnails (a build step and a cache for tens of journeys is machinery the
scale does not justify).

**Public and app shells (route groups).** Next.js route groups —
directories named `(group)` that organise layouts without appearing in the
URL — let the app declare a structural seam between the *front door*
(`/welcome`: pitch, walkthroughs, upload) and the *app* (life map,
adventures, candidates, imports) while every URL stays exactly as it is
today. Each group gets its own layout; the app shell's header gains a
reserved slot. This is the "auth-ready IA" constraint (§6) expressed as
file layout rather than as features.

## 2. Scope sources, and the one that has not arrived

Scope was assembled from four places:

1. The phase 6 close's known deltas (hover-card thumbnail never built,
   small-screen pass never driven beyond what phase 7 covered, life-map
   empty states never rendered against a real empty instance).
2. The recorded UI backlog (route thumbnail, small-screen pass,
   empty-state render check, zero-km routed narrative noise, fix-glyph
   legibility, poster/print view, dark theme, per-adventure export,
   unified timeline, backup download UI).
3. The maintainer's stated vision (2026-08-17): a richer front door
   carrying the product story; the life map as the signed-in landing; an
   adventure grid of plate covers; auth-ready IA as a light constraint;
   a committed viewport test suite.
4. Pilot feedback. **None has arrived yet.** The first pilot user has an
   instance but has not reported first impressions. The brief proceeds,
   but three scope decisions are explicitly provisional until that report
   lands: the grid's priority relative to the refinement sweep (§5.3),
   whether poster/print enters scope (§4, optional), and where the
   small-screen pass concentrates. If the report arrives mid-phase, its
   items join the maintainer's list at the next checkpoint boundary, not
   as scope creep mid-checkpoint.

A fifth source — the maintainer's own itch list — is supplied at this
brief's review and will be sorted into §3's buckets there.

## 4. What gets built — proposed checkpoints

- **CP1 — the Playwright harness.** Committed suite in `web/`, green
  against the *current* pages: the v1-loop layout truths phase 7 proved
  (made permanent), dialog focus behaviour, map smoke checks — at
  390/768/1280 px against the compose demo stack. No product changes in
  this checkpoint; the deliverable is the guard itself.
- **CP2 — refinement sweep, suite-driven.** Extend the suite to the
  phase 6 surfaces first, watch the known gaps fail, then fix: hover-card
  thumbnail (the SVG thumbnail component is built here and reused by
  CP4), fix-glyph legibility, zero-km wording, empty-state render
  verification against a scratch empty instance, small-screen pass. Web
  only; goldens byte-identical; Go untouched.
- **CP3 — grid mockups, at a STOP.** Static HTML mockups (demo data only,
  committed under `docs/phase-9/mockups/`) answering §5.1's placement
  question and the cover's exact contents. Review decides; DECISIONS.md
  records; nothing after this line is built before the STOP passes.
- **CP4 — the grid and the shells.** Route groups land the public/app
  seam and the reserved header slot; the grid is built as the mockups
  decided; `/welcome` absorbs the product-story evolution so the front
  door and the app shell are touched once, together; the suite extends to
  every new surface as it lands. (+ poster/print iff pulled into scope at
  Gate 1.)
- **CP5 — close.** A11y pass on everything new; README; cold
  `make test`; screenshots into `docs/screens/`; LOG.md. Phase not
  complete until the log exists.

Standing side-item, not phase scope: the first pilot user's device report
triggers the already-prepared follow-up commit (walkthrough verification
stamp + upload-copy line). If it fires mid-phase it lands as its own
commit, whatever checkpoint is open.

## 5. The real choices

**5.1 Where the grid lives.** Three candidates: (a) the summoned list
dialog *becomes* the grid — no new URL, but a dialog is a cramped home
for the phase's centrepiece and hostile to deep-linking; (b) a new
`/adventures` page — clean, linkable, the life map stays map-maximal,
costs one new nav item; (c) the home page becomes a hybrid map-over-grid
scroll — weakens the map-is-the-navigation decision from phase 6.
**Recommendation: mock (b) fully, mock (a) as the cheap contrast, do not
mock (c)** — it re-litigates a decided direction, which is exactly what
the mockup gate exists to prevent. Decided at CP3, not here.

**5.2 The zero-km routed noise.** Stationary gaps route to ~0 km legs and
the day narrative reads "road, 0.0 km" — true but noisy. Two treatments:
(a) presentation-side: the narrative and leg table render sub-threshold
routed legs as "stationary gap" wording, geometry untouched, threshold a
named parameter in the web layer; (b) pipeline-side: a min-chord floor in
`internal/journey` so such gaps never route. **Recommendation: (a) now,
(b) stays carried.** (a) keeps the phase's "Go untouched, goldens
byte-identical" property, is reversible, and the honest data stays
honest underneath. What would change this: evidence that the noise
distorts a *figure* (per-day km, provenance bar) rather than a line of
prose — then it is a data problem and (b) wins.

**5.3 Sequencing under missing feedback.** With the harness fixed at CP1
(maintainer's call, recorded in DECISIONS.md), the remaining question was
sweep-before-mockups or mockups-before-sweep. **Recommendation: sweep
first.** Every CP1/CP2 item is feedback-proof — no plausible pilot report
un-wants a legibility fix or a small-screen pass — while the grid is
exactly what first-impressions evidence should shape. Sequencing the
feedback-proof work first buys the pilot report time to arrive before the
mockup gate without idling the phase. What would change this: the report
arriving before Gate 1 passes, in which case its items sort into §3 at
the review and the order is re-checked.

## 6. Auth-ready IA — a named, light constraint

The maintainer states login is definitely coming eventually (a later,
charter-gated phase). This phase takes exactly three structural
consequences and nothing more:

1. An explicit seam between the front-door shell and the app shell
   (route groups, §1) so an auth gate later drops onto the seam without
   any page moving.
2. A reserved account slot in the app-shell header — empty or carrying
   the instance label today.
3. **No auth surfaces**: no forms, no dead buttons, no "coming soon".

The constraint stays light by construction: it shapes where files live,
never what gets built. It is not this phase's driver and no item may
grow because of it.

## 7. Verification standard

Unchanged from phase 6, plus the new harness: tsc/lint/build clean;
vitest green (existing tests plus whatever CP2/CP4 add); the Playwright
suite green against the compose demo stack at every checkpoint from CP1
on; goldens byte-identical; cold `make test` green with a zero Go diff
(the "presentation only" claim, proven again); keyboard walks driven on
the grid and the reshaped front door; contrast computed for anything new;
screenshots into `docs/screens/` (demo data only). Acceptance for CP3 is
the maintainer's review of the mockups; acceptance for CP4 is the
maintainer's browser.
