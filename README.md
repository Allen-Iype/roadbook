# Roadbook

Roadbook turns a Google Timeline export into a curated set of adventures. It
detects candidate journeys — periods away from home with a real destination —
and you confirm or dismiss each one. Confirmed adventures are drawn as routes
in which observed and inferred segments are always visibly distinct: what your
phone recorded is drawn as measurement, what the system inferred is drawn as
inference, and what it does not know stays visibly unknown.

That last sentence is the product's central rule. A journey is a list of legs,
each observed (your phone's own points) or a gap; a gap can be filled by road
routing, classified as a flight and drawn as an arc, or left as a plainly
marked unknown line. No geometry on the map ever hides its confidence.

## Supported input

The current on-device phone export, and only that: on Android, **Settings →
Location → Location Services → Timeline → Export Timeline data**. This export
carries your full history.

Two legacy Takeout-era formats — Semantic History (monthly `timelineObjects`
files) and `Records.json` (raw location samples) — are recognised and rejected
with a message naming them; they are not supported. Other wrong inputs
(encrypted Timeline backups, "My Activity" exports, KML, truncated JSON, and
similar) are likewise rejected with a message saying what the file is and what
to export instead.

## Try it with the demo dataset

The repository ships a demo you can run without handing over any real data:
three months of a fictional persona living in Reykjavík, generated by
committed code over real public geography. No person's history is in it.

You need Docker (with Compose). From a checkout:

```
docker compose up -d --build
mkdir -p data && cp testdata/demo/demo.json data/
docker compose run --rm api roadbook import -src /data/demo.json
docker compose run --rm api roadbook countries
docker compose run --rm api roadbook detect -from-db
```

Then open **http://127.0.0.1:3000**. The list shows 3 adventure candidates:
a dense south-coast drive to Höfn, a sparse Westfjords trip to Ísafjörður,
and an Akureyri weekend by air. The daily commute noise and a 44 km day trip
are correctly absent — near-home movement and trips without a far destination
are not adventures. Confirm a candidate with a name and open it: the Höfn
drive renders mostly observed legs; the Ísafjörður trip is dominated by
honestly unknown gaps (a handful of fixes across 455 road-km); the Akureyri
weekend draws its two flights as arcs, excluded from road-distance
validation.

Every number above reproduces from the repository:

```
make build
./bin/roadbook detect -src testdata/demo/demo.json
```

prints the parse counts (253 visits, 166 activities, 301 path points) and the
3 candidates with 1 home base and 0 outliers dropped;
`go run ./testdata/demo/gen` regenerates `testdata/demo/demo.json`
byte-identically. The regression test for these exact values is
`internal/detect/demo_test.go`.

## Run it against your own export

Put your export in `data/` (gitignored — nothing under it can be committed)
and import with an optional date window:

```
docker compose run --rm api roadbook import -src /data/Timeline.json
docker compose run --rm api roadbook detect -from-db
```

`-from` / `-to` (YYYY-MM-DD) restrict an import to a date range. Re-importing
the same or an overlapping export is safe: rows are content-hashed and
duplicates are skipped. Re-running detection — with different thresholds, or
after a new import — never touches your confirmations: decisions attach to
adventures by a stable identity and survive re-detection; every detection
run records the exact parameters that produced it.

The **Imports** page in the UI lists every import attempt, including failed
ones, with what the file turned out to be and what to do about it.

Photos can be attached to a confirmed adventure. Camera originals and Google
Photos Takeout files (with their JSON sidecars) carry position and time and
place themselves on the map and timeline; photos saved from messaging apps
have their metadata stripped at source and will honestly show as unplaced.
Only a thumbnail is stored — originals never touch the server's disk. A photo
that sits far from the inferred route is flagged, because a positioned photo
is the one ground truth that does not come from the same source as the route.

## What the deployment looks like

`docker compose up` runs three services: Postgres (with PostGIS), the Go API,
and the web frontend. Only the frontend is published to the host, and only on
loopback — `127.0.0.1:3000`. This is deliberate: the product has no
authentication, so exposing it beyond the machine it runs on is a decision
you must make explicitly, behind your own reverse proxy with access control.
The API and the database are not reachable from outside the compose network
at all; the browser talks only to the frontend, the frontend only to the API,
the API only to the database.

The database schema migrates automatically when the API container starts.
User data lives in named volumes (`pgdata` for the database, `photos` for
photo thumbnails); your export directory is mounted read-only.

### Configuration

Copy `.env.example` to `.env` and edit as needed. Every knob has a working
default — an empty or absent `.env` brings the stack up.

| variable | default | meaning |
|---|---|---|
| `POSTGRES_PASSWORD` | `roadbook` | compose-internal database password |
| `ROADBOOK_MAP_STYLE` | OpenFreeMap liberty | map style URL |
| `ROADBOOK_GEOCODER` | `none` | name suggestion at confirm time (`nominatim` to opt in) |
| `ROADBOOK_NOMINATIM_URL` | nominatim.openstreetmap.org | geocoder endpoint when opted in |

Map tiles are the one thing the browser fetches from a third party — the
viewport you look at leaks to the style's tile host. Point
`ROADBOOK_MAP_STYLE` at your own tile server to close even that. The
geocoder is off by default for the same reason: a self-hosted product makes
no surprise network calls.

## Routing, and what happens without it

Gaps between observations can be filled with road-following inference from
OSRM, run as an explicit batch step against a local OSRM instance — the
served application never depends on a routing service; it only reads answers
cached in Postgres. Without routing, gaps are drawn as straight lines that
say what they are. That degraded state is designed, not an error: the
product is fully usable with no routing at all. Air-speed gaps are
classified as flights and drawn as arcs either way.

Setting up OSRM (getting a regional OSM extract, preprocessing it, running
the batch) is documented in `docs/phase-3/OSRM.md`.

## Development without Docker

Go 1.25, Node 24, and a local Postgres 18 with PostGIS:

```
make build                # Go binary → bin/roadbook
DATABASE_URL=postgres://localhost/roadbook ./bin/roadbook migrate
./bin/roadbook serve      # API on :8080
cd web && npm ci && npm run dev   # frontend on :3000
make test                 # includes DB-backed store tests against a scratch database
```

`make test` finds a database by itself (local Postgres, or Docker as a
fallback) and creates scratch databases per test; it never touches an
existing database. The API contract is `api/openapi.yaml`; both the Go
server interfaces and the TypeScript client are generated from it
(`make generate`) and never edited by hand.

## Data safety

`data/` is gitignored wholesale and is where your exports and photo
thumbnails live in a non-Docker setup; nothing under it can be committed,
and the container mounts it read-only. Your Timeline export files are the
canonical copy of your history — keep them. An export's high-accuracy
`rawSignals` section covers only the ~30 days before the export was made and
then expires at the source, so exporting roughly monthly preserves what a
later export cannot recover.
